# Internationalisation (English and Spanish)

The site is served in two languages:

| Language | URL | `<html lang>` | hreflang |
| --- | --- | --- | --- |
| English | `/en` | `en` | `en` |
| Spanish (Spain) | `/es` | `es` | `es-ES` |

Both languages have a prefixed URL, so a URL always returns one language. Unprefixed URLs (`/`, `/about`) are only an entry point: the proxy redirects them to the visitor's language (see below). English is the fallback and the `x-default` hreflang.

## How it works

- `app/[lang]/layout.tsx` is the root layout. It sets `<html lang>`, builds the per-locale metadata and renders the JSON-LD.
- `app/[lang]/page.tsx` is the home page. Both locales are prerendered (`generateStaticParams`, `dynamicParams = false`), so any other value of `[lang]` is a 404.
- `proxy.ts` (called `middleware` in older Next versions) decides what to do with each request using the pure function `resolveRequest` in `lib/i18n/routing.ts`:
  - `/en`, `/es` and anything below them pass through.
  - Any other path is **redirected** to the visitor's locale, keeping path and query string: `/` to `/es`, `/about` to `/es/about`.
  - The locale is chosen in this order: the `NEXT_LOCALE` cookie, then `Accept-Language` (highest q-value whose primary subtag is supported, see `negotiateLocale`), then English.
  - The redirect is `308` when the result is English (crawlers send no `Accept-Language`, so old unprefixed English URLs transfer to `/en/...`) and `307` otherwise, because a Spanish result depends on the visitor. Both carry `Vary: Accept-Language, Cookie` and `Cache-Control: no-store`. The `no-store` matters: browsers cache a `308` with no expiry, which would pin a visitor to one language.
  - Unknown prefixes such as `/fr` are treated as unprefixed paths (`/en/fr`) and return 404.
- The EN | ES switcher (`components/language-switcher.tsx`) writes the `NEXT_LOCALE` cookie on click (`lib/i18n/language-choice.ts`, one year, `SameSite=Lax`). That is how an explicit choice beats the browser language on the next visit. There is no language banner and no geo-IP lookup: the browser's language is the signal.
- The proxy matcher is `/((?!api/|_next/|apple-icon$|opengraph-image$|twitter-image$|.*\\..*).*)`. Exclusions and why:
  - `api/`: the contact API is not localised by URL.
  - `_next/`: build assets.
  - `apple-icon$`, `opengraph-image$`, `twitter-image$`: extensionless metadata routes that live at the app root. Without the exclusion they would be redirected to `/en/...` and 404.
  - `.*\\..*`: anything with a file extension (`icon.svg`, `sitemap.xml`, `robots.txt`, `manifest.webmanifest`, `llms.txt`, images, PDFs).
- Matcher values must be constants, so the locale list cannot be interpolated into them. `resolveRequest` reads `locales` at runtime instead.

## Consent banner
- `components/consent-banner.tsx` (copy: `consent` in each dictionary) asks for cookie consent on every page. It is mounted once in `app/[lang]/layout.tsx`, first in the DOM, and fixed to the bottom of the viewport by `app/consent.css`. One banner serves both languages, with no location detection.
- The choice is stored in the first-party cookie `ps_consent` (`v1:accepted` or `v1:rejected`, 12 months, see `lib/consent.ts`). Raise `policyVersion` there when the policy changes so everyone is asked again.
- Necessary: `NEXT_LOCALE` and `ps_consent`. Optional: AWS CloudWatch RUM (`cwr_s`, `cwr_u`). `components/rum-script.tsx` injects the snippet from `lib/rum.ts` only after Accept. Reject deletes `cwr_s` and `cwr_u` and reloads the page if RUM was already loaded in that page view.
- The footer "Cookie settings" button and the one in the Privacy Policy page reopen the banner. The Privacy Policy page (`/privacy`, `/es/privacy`) has `[TO CONFIRM: ...]` markers to resolve before launch.
- Add any new optional script (analytics, ads, embeds) behind the same consent check and list it in `privacyPage.cookieTable`.
- The Spanish copy needs a native review before launch, like the rest of `es.ts`.

## Catalogue pages

Industry and product pages are generated from `lib/catalogue` (`app/[lang]/industries/[industry]`, `app/[lang]/solutions/[product]`, plus the `/problems`, `/industries` and `/solutions` indexes). To add a product or industry: add its id and relations in `structure.ts`, write its copy in both `catalogue-*.ts` files (types list what is missing), add its media slot in `lib/media.ts` and `media` in both dictionaries, then build. The six old team pages redirect (308) to products.

## Adding a page under `app/[lang]/`

The About page (`app/[lang]/about/page.tsx`, `/about` and `/es/about`) is the pattern to copy.

1. Create `app/[lang]/<name>/page.tsx` with `generateStaticParams` (both locales) and `dynamicParams = false`. Put the copy in a new key of `lib/i18n/en.ts` and `es.ts` (`aboutPage`).
2. `generateMetadata`: canonical is `localePath(lang, "/<name>")`, alternates come from `languageAlternates("/<name>")` in `lib/alternates.ts` (en, es-ES, x-default). Setting `openGraph` or `twitter` replaces the layout's object, so carry over the `images` from `parent` as the About page does. Use `title: { absolute }` when the title already names the company, otherwise the layout template adds ` | ProcessSpark`.
3. Render `<Header page="<name>" />` and `<Footer page="<name>" />` (add the id to `PageId` in `components/site-link.tsx`). The proxy needs no change: `/<name>` is redirected to the visitor's locale.
4. Add the page to `app/sitemap.ts` (with `languageAlternates`) and, if it should be listed, `lib/llms.ts`.
5. Structured data lives in each page, not in the layout (the home page renders `StructuredData`, the About page `AboutStructuredData`), so a page never claims to be the home page.

How nav links resolve:
- Hash links (`#problems`, `#contact`) only exist on the landing page. `sectionHref(lang, page, hash)` in `components/site-link.tsx` keeps them as plain `#hash` anchors on the landing page and turns them into `/en#hash` or `/es#hash` on any other page.
- `SiteLink` renders a plain `<a>` for hash-only hrefs and `next/link` for routes. The logo goes to `localePath(lang)`.
- Page links use `localePath(lang, "/about")`. The current page gets `aria-current="page"`.
- The EN | ES switcher takes the locale-less `path` (`/about` on the About page). 
- `<html data-scroll-behavior="smooth">` lets Next navigate to `/#section` without fighting the CSS smooth scroll.
- The header has two panels, "What we solve" and "Solutions" (both labels are links, a chevron button opens each panel), plus About, Downloads (Descargas), the language switch and a "Book a call" button. Both panels are built from the catalogue (`menus()` in `lib/catalogue/index.ts`). The desktop nav shows from 1031px in English and 1201px in Spanish (measured: at least 24px to spare before the language switch); below that the mobile menu is used. See `app/about.css`.
- Problem items in the menu link to `/{lang}/problems#<id>` through `next/link` everywhere, the hub included. The header also dispatches `ps:problem-select` (`lib/problem-select.ts`) so the hub's selector reacts when the URL does not change. The selector acts on the initial hash, that event and `hashchange`.

## Editing copy

1. Change the English text in `lib/i18n/en.ts`.
2. Change the matching text in `lib/i18n/es.ts`.
3. Run `npm run build` (or `npx tsc --noEmit`).

`es.ts` is typed against `Dictionary`, so a key that exists in English but not in Spanish (or the other way round) fails the build. Strings are plain text. Markup (spans, line breaks) is applied by the components, so lines that wrap in a fixed place are separate keys (`line1`, `line2`, `accent`).

Structure that must not change per language (ids, icons, order, image paths, the form option values sent to the API) stays in `lib/content.ts` and `lib/media.ts`. Components read text by id, for example `dict.useCases.items[id]`.

Client components (`header.tsx`, `process-explorer.tsx`, `process-brief.tsx`) never import a dictionary. They receive the slice they need as props and use `import type { Dictionary }` only. Keep it that way, otherwise both languages end up in the browser bundle.

Spanish style: castellano de España, informal "tú", no exclamation marks, no em dashes, product names translated (Habla con tus datos, Portal de proveedores...; names are in `lib/i18n/catalogue-es.ts`), acronyms untranslated, "IA" for "AI". The Spanish site says "Descargas" for Downloads and "Sectores" for Industries; URLs keep English slugs.

## Adding a language

1. `lib/i18n/config.ts`: add the code to `locales`, and an entry in `htmlLang`, `hreflang`, `ogLocale` and `localeCodes`.
2. Create `lib/i18n/xx.ts` exporting a `Dictionary` and register it in `lib/i18n/index.ts`. Add the language name to `languageSwitcher` in every dictionary.
3. Create `app/xx/llms.txt/route.ts`, copying `app/es/llms.txt/route.ts`.
4. Fix anything else the compiler flags (it flags every `Record<Locale, ...>`).

The proxy, metadata, hreflang alternates, sitemap, JSON-LD, social image route and contact API pick the new locale up from `locales`.

## SEO behaviour

- Canonical is the page's own URL (`/en` or `/es`).
- Every page lists `<link rel="alternate" hreflang>` for `en`, `es-ES` and `x-default` (the English URL, `/en/...`), itself included, with absolute URLs from `lib/site.ts`.
- `sitemap.xml` lists every page in both languages (home, problems hub, industries and each industry, solutions and each product, About, Downloads, Privacy), generated from the catalogue ids, each with the same three alternates.
- `robots.txt` is unchanged (`allow: /` covers both).
- Open Graph and Twitter: localised title, description and image alt. Spanish adds `og:locale` `es_ES` and uses `/es/social-image`. English uses `/opengraph-image` and `/twitter-image` and does not emit `og:locale`.
- JSON-LD: `inLanguage` is `en` or `es-ES`, names and descriptions are localised. `WebSite` and `WebPage` ids are per language, the `Organization` id is shared. `availableLanguage` is `["en", "es"]` on both pages (assumes the team can reply in Spanish).
- `/llms.txt` is English, `/es/llms.txt` is Spanish. `app/manifest.ts` stays English.

## Contact form and API

- The form posts the field names it always did (`name`, `email`, `company`, `category`, `process`, `website`) plus `lang` (the page locale). `website` is still the honeypot.
- `category` option values stay English (that is what the team reads). Only the visible labels are translated.
- `app/api/contact/route.ts` accepts `lang` if it is in `locales`. Any other value, or none, means English. It never causes a 400.
- The team notification is always English, keeps reply-to as the submitter and both team addresses, and has a `Language: es|en` line.
- The confirmation to the submitter is in the page language (`emails.confirmation` in each dictionary). Fixed template: only the first name is echoed, no free text, no response-time promise, no exclamation marks, no em dashes, HTML-escaped.

## Images

Images are shared between languages and some contain English text baked into the picture (dashboard screenshots, checklists). Only `alt` text and placeholder labels are translated (`dict.media`). Producing Spanish versions of those images is a known limitation. The overview PDF is also English only, and the Spanish link says so.

## Known limitations

- `app/global-not-found.tsx` and `experimental.globalNotFound` in `next.config.ts` are needed because the root layout sits under `[lang]`. The flag is experimental. The 404 page is English.
- `proxy.ts` is not verified on AWS Amplify until a real deploy. If Amplify does not apply it, unprefixed URLs would 404. The language-based redirect cannot be expressed in `next.config.ts` `redirects()` with a cookie and header condition as cleanly, so check the first deploy. Also check that the CDN honours `Vary: Accept-Language, Cookie` on the redirects, otherwise one visitor's redirect could be served to another.
- Uppercase locale prefixes (`/ES`) are a 404.
- Visitors are never matched by country, only by browser language.
- The Spanish copy is a draft and needs a native review.
