# Internationalisation (English and Spanish)

The site is served in two languages:

| Language | URL | `<html lang>` | hreflang |
| --- | --- | --- | --- |
| English (default) | `/` | `en` | `en` |
| Spanish (Spain) | `/es` | `es` | `es-ES` |

English keeps its original, unprefixed URLs. There is no automatic language detection (no `Accept-Language` redirect, no cookie), so a URL always returns the same language. This keeps pages cacheable and search engines happy.

## How it works

- `app/[lang]/layout.tsx` is the root layout. It sets `<html lang>`, builds the per-locale metadata and renders the JSON-LD.
- `app/[lang]/page.tsx` is the home page. Both locales are prerendered (`generateStaticParams`, `dynamicParams = false`), so any other value of `[lang]` is a 404.
- `proxy.ts` (called `middleware` in older Next versions) decides what to do with each request using the pure function `resolveRequest` in `lib/i18n/routing.ts`:
  - `/` and any other unprefixed path is **rewritten** to `/en/...`. The browser URL stays unprefixed.
  - `/en` and `/en/...` get a `308` redirect to the unprefixed URL (query string kept), so there is only one URL for English.
  - `/es` and `/es/...` pass through.
  - Unknown prefixes such as `/fr` fall into the first rule (`/en/fr`) and return 404.
- The proxy matcher is `/((?!api/|_next/|apple-icon$|opengraph-image$|twitter-image$|.*\\..*).*)`. Exclusions and why:
  - `api/`: the contact API is not localised by URL.
  - `_next/`: build assets.
  - `apple-icon$`, `opengraph-image$`, `twitter-image$`: extensionless metadata routes that live at the app root. Without the exclusion they would be rewritten to `/en/...` and 404.
  - `.*\\..*`: anything with a file extension (`icon.svg`, `sitemap.xml`, `robots.txt`, `manifest.webmanifest`, `llms.txt`, images, PDFs).
- Matcher values must be constants, so the locale list cannot be interpolated into them. `resolveRequest` reads `locales` at runtime instead.

## Adding a page under `app/[lang]/`

The About page (`app/[lang]/about/page.tsx`, `/about` and `/es/about`) is the pattern to copy.

1. Create `app/[lang]/<name>/page.tsx` with `generateStaticParams` (both locales) and `dynamicParams = false`. Put the copy in a new key of `lib/i18n/en.ts` and `es.ts` (`aboutPage`).
2. `generateMetadata`: canonical is `localePath(lang, "/<name>")`, alternates come from `languageAlternates("/<name>")` in `lib/alternates.ts` (en, es-ES, x-default). Setting `openGraph` or `twitter` replaces the layout's object, so carry over the `images` from `parent` as the About page does. Use `title: { absolute }` when the title already names the company, otherwise the layout template adds ` | ProcessSpark`.
3. Render `<Header page="<name>" />` and `<Footer page="<name>" />` (add the id to `PageId` in `components/site-link.tsx`). The proxy needs no change: `/<name>` is rewritten to `/en/<name>` and `/es/<name>` passes through.
4. Add the page to `app/sitemap.ts` (with `languageAlternates`) and, if it should be listed, `lib/llms.ts`.
5. Structured data lives in each page, not in the layout (the home page renders `StructuredData`, the About page `AboutStructuredData`), so a page never claims to be the home page.

How nav links resolve:
- Hash links (`#problems`, `#contact`) only exist on the landing page. `sectionHref(lang, page, hash)` in `components/site-link.tsx` keeps them as plain `#hash` anchors on the landing page and turns them into `/#hash` (English) or `/es#hash` (Spanish) on any other page.
- `SiteLink` renders a plain `<a>` for hash-only hrefs and `next/link` for routes. The logo goes to `localePath(lang)`.
- Page links use `localePath(lang, "/about")`. The current page gets `aria-current="page"`.
- The EN | ES switcher takes the locale-less `path` (`/about` on the About page). The language banner derives it from `usePathname()`.
- `<html data-scroll-behavior="smooth">` lets Next navigate to `/#section` without fighting the CSS smooth scroll.
- The header nav has five links. It collapses into the mobile menu below 920px (English) and 1010px (Spanish, longer labels). See `app/about.css`.

## Language suggestion banner
English pages show a small dismissible bar ("¿Prefieres ver esta web en español?" with a "Ver en español" link to `/es`) to visitors whose browser prefers Spanish.
- **Client-only detection.** `components/language-banner.tsx` runs in `useEffect` after hydration and reads `navigator.languages` (fallback `navigator.language`). It shows when a `es*` language appears before any `en*` one, or when only `es*` is present. The server never sees the language, so the HTML is identical for every visitor and both pages stay static and cacheable.
- **Why no redirect.** Crawlers (Googlebot is en-US) must always get the same page at the same URL, and a redirect would also trap people who want English. A suggestion leaves the choice to the visitor.
- **No layout shift.** The bar is `position: fixed` (styles in `app/language-switcher.css`) and mounts only after hydration. It sits at `z-index: 30`, below the sticky header (40) that holds the open mobile menu.
- **Persistence.** `localStorage` key `ps-lang-suggestion` (all access in try/catch). It is set when the visitor dismisses the bar, clicks "Ver en español", or uses the EN | ES switcher (`components/language-switcher.tsx`), so anyone who picked a language is not asked again.
- **Never on `/es`.** The component renders `null` for any locale other than `en`.
- **Copy.** The three Spanish strings live in `lib/i18n/language-suggestion.ts`, not in the dictionaries (they are Spanish on an English page, and the dictionary types must match across locales). The elements carry `lang="es"`.
- **To remove it.** Delete `components/language-banner.tsx`, its `<LanguageBanner>` in `app/[lang]/layout.tsx`, the `.lang-banner` block in `app/language-switcher.css`, and `lib/i18n/language-suggestion.ts`. Also drop the `onClick` and `"use client"` from the switcher.
## File map

| File | Purpose |
| --- | --- |
| `lib/i18n/config.ts` | `locales`, `defaultLocale`, `htmlLang`, `hreflang`, `ogLocale`, `localePath()`, `socialImagePath()`. No dictionary imports, safe in the proxy and in client code. |
| `lib/i18n/routing.ts` | Pure routing rules used by `proxy.ts`. |
| `lib/i18n/en.ts` | English copy. Defines the `Dictionary` type. |
| `lib/i18n/es.ts` | Spanish copy, typed as `Dictionary`. All Spanish text lives here. |
| `lib/i18n/index.ts` | `getDictionary(locale)` (server side) and re-exports. |
| `lib/content.ts`, `lib/media.ts`, `lib/site.ts` | Language-independent structure: ids, icons, order, media sources, form values. |
| `components/language-switcher.tsx`, `app/language-switcher.css` | EN / ES switch (header, mobile menu, footer). |
| `lib/llms.ts`, `app/llms.txt/route.ts`, `app/es/llms.txt/route.ts` | `/llms.txt` (English) and `/es/llms.txt` (Spanish). |
| `app/[lang]/social-image/route.tsx`, `lib/og.tsx` | Open Graph and Twitter image for non-default locales. |
| `app/global-not-found.tsx` | 404 page (see limitations). |

## Editing copy

1. Change the English text in `lib/i18n/en.ts`.
2. Change the matching text in `lib/i18n/es.ts`.
3. Run `npm run build` (or `npx tsc --noEmit`).

`es.ts` is typed against `Dictionary`, so a key that exists in English but not in Spanish (or the other way round) fails the build. Strings are plain text. Markup (spans, line breaks) is applied by the components, so lines that wrap in a fixed place are separate keys (`line1`, `line2`, `accent`).

Structure that must not change per language (ids, icons, order, image paths, the form option values sent to the API) stays in `lib/content.ts` and `lib/media.ts`. Components read text by id, for example `dict.useCases.items[id]`.

Client components (`header.tsx`, `process-explorer.tsx`, `process-brief.tsx`) never import a dictionary. They receive the slice they need as props and use `import type { Dictionary }` only. Keep it that way, otherwise both languages end up in the browser bundle.

Spanish style: castellano de España, informal "tú", no exclamation marks, no em dashes, product and acronym names untranslated, "IA" for "AI".

## Adding a language

1. `lib/i18n/config.ts`: add the code to `locales`, and an entry in `htmlLang`, `hreflang`, `ogLocale` and `localeCodes`.
2. Create `lib/i18n/xx.ts` exporting a `Dictionary` and register it in `lib/i18n/index.ts`. Add the language name to `languageSwitcher` in every dictionary.
3. Create `app/xx/llms.txt/route.ts`, copying `app/es/llms.txt/route.ts`.
4. Fix anything else the compiler flags (it flags every `Record<Locale, ...>`).

The proxy, metadata, hreflang alternates, sitemap, JSON-LD, social image route and contact API pick the new locale up from `locales`.

## SEO behaviour

- Canonical is the page's own URL (`/` or `/es`).
- Every page lists `<link rel="alternate" hreflang>` for `en`, `es-ES` and `x-default` (the English URL), itself included, with absolute URLs from `lib/site.ts`.
- `sitemap.xml` lists the home and About pages in both languages, each with the same three alternates.
- `robots.txt` is unchanged (`allow: /` covers `/es`).
- Open Graph and Twitter: localised title, description and image alt. Spanish adds `og:locale` `es_ES` and uses `/es/social-image`. English keeps `/opengraph-image` and `/twitter-image` and does not emit `og:locale`.
- JSON-LD: `inLanguage` is `en` or `es-ES`, names and descriptions are localised. `WebSite` and `WebPage` ids are per language, the `Organization` id is shared. `availableLanguage` is `["en", "es"]` on both pages (assumes the team can reply in Spanish).
- `/llms.txt` is English, `/es/llms.txt` is Spanish. `app/manifest.ts` stays English.

## Contact form and API

- The form posts the field names it always did (`name`, `email`, `company`, `category`, `process`, `website`) plus `lang` (the page locale). `website` is still the honeypot.
- `category` option values stay English (that is what the team reads). Only the visible labels are translated.
- `app/api/contact/route.ts` accepts `lang` if it is in `locales`. Any other value, or none, means English. It never causes a 400.
- The team notification is always English, keeps reply-to as the submitter and both team addresses, and has a `Language: es|en` line.
- The confirmation to the submitter is in the page language (`emails.confirmation` in each dictionary). Fixed template: only the first name is echoed, no free text, no response-time promise, no exclamation marks, no em dashes, HTML-escaped.

## Images

Images are shared between languages and some contain English text baked into the picture (dashboard screenshots, checklists). Only `alt` text and placeholder labels are translated (`dict.media`). Producing Spanish versions of those images is a known limitation. The overview PDF is also English only, and the Spanish link says so.

## Known limitations

- `app/global-not-found.tsx` and `experimental.globalNotFound` in `next.config.ts` are needed because the root layout sits under `[lang]`. The flag is experimental. The 404 page is English.
- `proxy.ts` is not verified on AWS Amplify until a real deploy. If Amplify does not apply it, the same rules can be expressed in `next.config.ts`: a `redirects()` entry for `/en/:path*`, and a `rewrites()` entry (`beforeFiles`) sending unprefixed paths to `/en/:path*`.
- `/en/` redirects twice (`/en/` to `/en` to `/`).
- Uppercase locale prefixes (`/ES`) are a 404.
- The header links wrap onto two lines between 851 and about 1000 px in Spanish.
- The Spanish copy is a draft and needs a native review.
